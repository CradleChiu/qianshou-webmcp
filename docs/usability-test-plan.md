# 目標使用者可用性測試計畫

> 測試版本：P1 官方資料試行版
> 基準提交：執行測試前填入 Git commit hash
> 目的：確認視障使用者能否獨立取得、理解並核對行前交通資訊
> 安全限制：資料雖來自 TDX、中央氣象署、OpenTripPlanner 與 OpenStreetMap，仍不得把測試結果當成實際出行或道路安全保證

## 1. 本輪要回答的問題

1. 使用者能否不用主持人提示，完成起訖點、偏好與查詢？
2. 使用者能否分辨「官方資料」、「整合計算」與「目前未知」？
3. 行程摘要的順序、用詞與朗讀內容，是否符合視障者行前決策需求？
4. 發生輸入錯誤或上游 unavailable 時，使用者是否知道下一步？
5. 手機與桌面螢幕閱讀器是否都能完成相同核心工作？
6. 只說目的地時，使用者能否理解一次性定位授權，並在拒絕後用附近地標接續？

本輪不評估導航途中使用、過馬路判斷，也不以一次場測比較裝置 GPS 準確度；但會評估定位權限、誤差說明與失敗復原是否容易理解。自動化測試不能取代真人回饋。

## 2. 優先使用者與樣本

第一輪招募 3 至 5 位平常使用螢幕閱讀器或語音操作、能自主決定出行方式的台灣成年視障者：

- 至少 2 位使用手機螢幕閱讀器，其中至少涵蓋 VoiceOver 或 TalkBack。
- 至少 1 位使用桌面螢幕閱讀器，其中至少涵蓋 NVDA、JAWS 或 macOS VoiceOver。
- 優先讓參與者使用自己的裝置、瀏覽器、語速、放大與輸入設定。

高齡者是第二組，不與視障組合併計算。若本輪同時測試，另招募 2 位並分開整理閱讀、記憶、觸控與行動需求。

## 3. 測試矩陣

每場至少記錄下列環境；缺少的組合必須在報告中列為未驗證，不得以模擬 viewport 宣稱完成。

| 類型 | 優先組合 | 本輪最低要求 |
|---|---|---:|
| 桌面 | Windows＋Chrome／Edge＋NVDA | 1 人 |
| iPhone | iOS＋Safari＋VoiceOver | 1 人，若受招募限制則列為未驗證 |
| Android | Android＋Chrome＋TalkBack | 1 人，若受招募限制則列為未驗證 |
| 放大／大字 | 200% zoom 或系統大字 | 至少 1 場附加檢查 |
| 原生 WebMCP | 支援 `document.modelContext` 的瀏覽器 | 有可用 runtime 才執行，結果與人工 UI 分開報告 |

## 4. 測試前準備

主持人於每場開始前完成：

1. 記錄日期、Git commit、網址、裝置、OS、瀏覽器、輔具與版本。
2. 確認 OTP、TDX 與 CWA 服務狀態；保留測試開始時的資料來源與取得時間截圖。
3. 使用公共場所情境，不要求或保存住家、常用地址或其他敏感地點。
4. 說明錄音、錄影、螢幕錄製與輔具資訊的保存方式，取得同意後才開始。
5. 告知參與者可隨時休息、略過問題或停止，不影響任何權益。
6. 關閉主持人自己的自動填寫與瀏覽器擴充功能，避免干擾結果。
7. 為 unavailable 情境準備可重現方式；不要在正式任務進行中臨時破壞服務。
8. 將瀏覽器定位權限重設為「詢問」，並另準備一次拒絕定位的復原情境；不得保存參與者的實際座標。

若正式資料服務當天不穩定，記錄實際 unavailable 體驗；不可切換成未標示的固定答案來完成測試。

## 5. 主持人開場稿

「我們正在測試產品，不是在測試你。畫面會使用官方交通與天氣資料，也會包含系統整合計算；它們可能延遲、不完整或暫時無法取得，不能取代你平常的出行判斷與輔具。請用你平常的方式操作，並把你期待發生什麼、哪裡不確定說出來。我會先觀察與記錄，必要時才提供提示。」

## 6. 核心任務

主持人不要先示範操作，也不要預先說出控制項名稱。除任務 E 外，使用臺北車站到臺大醫院的公共場所情境，避免參與者提供個人地址。

### 任務 A：判斷資料能不能信任

請參與者在還沒查詢前說明：這個產品提供什麼、資料來自哪裡，以及是否可以把結果當成道路安全保證。

觀察：是否能分辨「官方來源」與「系統整合路線」，是否理解未知與限制。

### 任務 B：建立行程

情境：「你想從臺北車站前往臺大醫院，希望少走路、少轉乘，而且需要無階梯動線。」

觀察：能否找到起點、目的地、三項偏好與主要操作；是否理解每個偏好的效果不是保證。

### 任務 B2：只說目的地並處理定位

情境：「你現在位於主持人事先確認的公共場所，只說『我想去台北101』。」先讓參與者允許一次定位；第二輪重設權限後選擇拒絕，再用附近公共地標接續。

觀察：是否理解定位用途、是否聽到成功或失敗狀態、拒絕後目的地是否保留，以及能否找到「再試一次定位」或直接說附近地標。記錄裝置回報的誤差範圍，但不記錄經緯度。

### 任務 C：理解結果與決定下一步

請參與者說出：

1. 預估總時間、步行時間與轉乘次數。
2. 建議先搭什麼，以及哪個資訊最值得出發前再次確認。
3. 哪些是靜態或整合計算，哪些可能是即時資料。
4. 哪一項無障礙資訊仍未知或不完整。
5. 「相對較適合」是否只被理解為候選間比較，而不是無障礙、安全或可通行保證。

觀察：參與者實際先尋找的三項內容，而不是只核對畫面是否有欄位。

### 任務 D：控制朗讀

請參與者開始朗讀、暫停、繼續，再停止朗讀。

觀察：按鈕名稱與狀態是否被正確宣告；朗讀順序是否符合決策需求；內容是否太長、重複或缺少來源與限制。

### 任務 E：修正錯誤

請參與者將起點與目的地設為相同地點後送出，再自行修正。若環境允許，接著呈現一次已事先準備的 unavailable 狀態。

觀察：是否聽到錯誤、焦點是否到正確欄位、是否知道如何復原；遇到 unavailable 時是否知道稍後重試或改查官方來源。

### 任務 F：核對到站、天氣與來源

請參與者找出下一班車、天氣、資料觀測時間、系統取得時間與目前限制，並用自己的話說明三者是否能共同代表現在的街道狀況。

觀察：「產生時間」是否被誤解為官方更新時間，以及折疊的來源內容是否容易發現。

### 任務 G：用自己的說法重新描述

請參與者說出，如果用平常的說法詢問同一趟旅程，會怎麼講；再指出畫面中最不像台灣日常用語的三個詞。

這項結果用於地名別稱、語音輸入與內容設計，不直接把單一參與者用詞推論成所有人的偏好。

### 任務 H：原生 WebMCP（選測）

只在瀏覽器原生提供 `document.modelContext` 時執行。請參與者直接用平常說法告訴 Agent，例如「我想從台北車站去台大醫院，少走路而且不要走樓梯，順便告訴我等車和天氣」，不得提示或指定工具名稱。再確認 Agent 是否自行完成查詢、歧義時是否用地點名稱請人確認、頁面是否同步顯示，以及使用者能否修改或否決。

未提供原生 runtime 時標記為 `UNAVAILABLE`，test double 只能作為工程回歸證據。

## 7. 記錄方式

每項任務統一記錄：

- 結果：獨立完成／一次提示後完成／多次提示後完成／未完成／環境不可用。
- 完成時間、返回次數、輸入錯誤數與主持人提示數。
- 任務後難度評分：1（非常容易）至 7（非常困難）。
- 參與者原話與觀察到的操作策略。
- 使用裝置、瀏覽器、輔具、語速、放大比例及輸入方式。
- 問題嚴重度：P0 阻止核心任務或造成安全誤解；P1 明顯困難；P2 可改善。
- 問題層級：內容／互動／輔具相容性／資料品質／效能／服務可用性。

每位參與者使用 [`usability-session-record.md`](usability-session-record.md) 建立一份獨立紀錄；對外報告前移除姓名、聯絡方式與敏感內容。

## 8. 測試後問題

1. 哪一段最容易？哪一段最不確定？
2. 如果只能先聽三項資訊，會選哪三項？順序是什麼？
3. 哪些數字看起來像即時資料，但其實不確定？
4. 「整合資料」、「取得時間」、「未知」這些詞是否清楚？
5. 你期待如何輸入地點：打字、語音、常用地點、附近站牌，還是其他方式？
6. 服務暫時無法取得時，你希望產品提供什麼下一步？
7. 哪些用詞不像你平常會說的話？
8. 有沒有任何內容讓你誤以為系統能保證無障礙或道路安全？

## 9. 第一輪通過標準

- 至少 80% 的核心任務 A–F 可在沒有主持人提示下完成。
- 100% 的參與者知道路線是整合計算，不能視為道路安全或無障礙保證。
- 100% 的參與者能找到至少一項資料限制或未知事項。
- 100% 的參與者不把「依目前已標記資料，相對較適合」理解成全程無階梯、適合視障者或現場可通行保證。
- 沒有鍵盤陷阱，主要流程可由受測的螢幕閱讀器完成。
- 所有 P0 問題完成修正與回歸後，才能擴張新的城市、運具或自動化代理行為。
- 至少找出並修正一項研究文件或自動化測試未預見的問題。

未達標不代表參與者失敗，而是產品尚未達到本輪門檻。

## 10. 停止與升級規則

遇到下列任一情況，停止該任務並記為 P0：

- 參與者把系統結果當成可以安全過馬路或保證無階梯的指示。
- 焦點陷入、無法離開控制項，或核心結果完全無法被輔具取得。
- 系統顯示的來源、時間或 unavailable 狀態與實際服務狀態不一致。
- 測試要求參與者透露未同意提供的敏感地點或個人資料。

## 11. 產出與下一階段決策

測試後產出：

1. 一頁摘要：樣本、環境涵蓋、核心任務獨立完成率與前三大問題。
2. P0／P1／P2 清單，每項附證據、影響與建議調整。
3. 視障者與高齡者分組觀察，不用單一平均值掩蓋差異。
4. 未驗證矩陣：實體裝置、輔具、原生 WebMCP 或服務情境。
5. 下一輪要驗證的假設與明確 go／no-go 決定。

只有完成 P0 修正與至少一輪目標使用者驗證後，才重新評估 PostGIS、更多縣市、Shape、即時路線整合或語音代理的優先順序。
